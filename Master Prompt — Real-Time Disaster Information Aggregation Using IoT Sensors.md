You are an expert IoT, embedded-systems, disaster-management, backend, frontend, and hackathon-project architect. Help us design and build a complete working prototype for a hackathon project titled **“Real-Time Disaster Information Aggregation Using IoT Sensors.”** The project is intended primarily for rural and remote areas where internet connectivity may be weak, intermittent, or completely unavailable. The system must combine multiple distributed IoT sensor nodes, communicate using LoRa, aggregate the sensor information, calculate disaster-risk levels, and provide real-time local alerts and a dashboard. The system should be practical enough to demonstrate physically during a hackathon rather than being only a theoretical concept.

The project will use exactly **three ESP32 boards** and **three LoRa modules**, with an antenna associated with each LoRa module. The available sensors/components are a **BMP280 pressure and temperature sensor, vibration/shock sensor, soil-moisture sensor, rain sensor, and ultrasonic sensor**. These components should be distributed across three nodes called **Node 1, Node 2, and Node 3**. The architecture should prioritize low-power, long-range communication and should not depend on continuous Wi-Fi or internet connectivity. Every hardware connection, sensor role, communication method, and software component should be clearly explained.

**Node 1** will be the **Mountain/Landslide Monitoring Node**. It will be physically positioned in a mountainous or hilly region. Node 1 will contain an ESP32, LoRa module, antenna, soil-moisture sensor, and vibration/shock sensor. Its main purpose is to monitor environmental conditions associated with increased landslide risk. The soil-moisture sensor measures the amount of water in the soil, while the vibration/shock sensor detects unusual ground vibrations or movement. Node 1 should continuously read these sensors, perform basic local processing, determine a local risk state, and transmit its readings and status through LoRa.

The landslide-monitoring logic must not falsely claim that the sensors can guarantee or perfectly predict a landslide. Instead, the system should identify **conditions associated with increased landslide risk**. For example, normal soil moisture combined with normal vibration should produce a LOW or SAFE condition, while very high soil moisture combined with elevated vibration should produce a HIGH or CRITICAL risk condition. The system should consider both measurements together rather than relying on a single sensor. Explain how calibration, thresholds, sensor noise, and environmental conditions should be handled.

**Node 2** will be the **River/Flood Monitoring Node**. It will be positioned near a river, stream, dam, reservoir, or other water body. Node 2 will contain an ESP32, LoRa module, antenna, ultrasonic sensor, and BMP280 sensor. The ultrasonic sensor will measure the distance between the sensor and the water surface. If the ultrasonic sensor is mounted at a known height, the system should calculate water level using the relationship **Water Level = Sensor Mounting Height − Measured Distance**. Node 2 should continuously monitor water level and transmit the measurements through LoRa.

The **BMP280** on Node 2 should measure atmospheric pressure and temperature. These values should be treated as environmental/context information rather than being falsely represented as direct flood predictors. The main flood indicators should be water level, rate of water-level increase, and rainfall information. The software should maintain historical water-level readings so that it can identify whether the water level is stable, slowly increasing, or rapidly increasing. The system should therefore consider both the current water level and its trend.

**Node 3** should be designed as the **Rain Monitoring and Field Aggregator Node**. It will contain the third ESP32, third LoRa module, antenna, and rain sensor. Node 3 should monitor rainfall while also receiving LoRa data from Node 1 and Node 2. It should therefore act as the local field-level data aggregation point. Node 1 and Node 2 send their sensor readings to Node 3 over LoRa, and Node 3 combines these readings with its own rainfall data. This architecture makes Node 3 more than a simple sensor node: it becomes the central field aggregator for the three-node rural disaster-monitoring network.

The communication architecture should use **LoRa as the primary communication method between the field nodes**. Do not make Wi-Fi or internet connectivity a requirement for communication between Node 1, Node 2, and Node 3. The basic architecture should be **Node 1 → LoRa → Node 3** and **Node 2 → LoRa → Node 3**, with Node 3 also monitoring rainfall. The system should use suitable packet formats, node IDs, timestamps or packet IDs, sensor values, and status information. Explain how the LoRa network should be configured, how packets should be transmitted and received, and how the system can detect missing or invalid packets.

The project must support **three operating levels**. In the first level, the system should continue working even when there is no internet connection. The ESP32 nodes should still read sensors, communicate over LoRa, and perform basic local risk calculations. In the second level, Node 3 can be connected through USB/Serial to a local laptop or computer. The laptop can run the backend and dashboard completely on the local network without requiring internet access. In the third level, if internet connectivity is available, the system may optionally upload data to a cloud service or remote monitoring system. However, cloud connectivity must remain optional and must never be required for the core disaster-monitoring functionality.

The recommended physical architecture should therefore be **Node 1 in the mountain region, Node 2 near the river, and Node 3 acting as the rain-monitoring and field aggregation point**. Node 1 communicates with Node 3 using LoRa, Node 2 communicates with Node 3 using LoRa, and Node 3 connects to a local gateway computer through USB/Serial for the hackathon prototype. The local computer runs the backend, database, risk engine, and dashboard. This approach provides a practical demonstration of how the system can operate in rural areas without depending on cellular internet.

The ESP32 firmware should be written primarily in **C/C++**, using the Arduino framework through Arduino IDE or PlatformIO. The ESP32 programs must handle sensor initialization, sensor readings, filtering, calibration, threshold checking, LoRa communication, packet formation, error handling, and local risk calculations. Node 1 firmware should specifically handle the soil-moisture and vibration sensors. Node 2 firmware should handle the ultrasonic sensor and BMP280. Node 3 firmware should handle the rain sensor, LoRa reception, packet aggregation, and forwarding of the combined information to the local gateway.

Design clear and structured LoRa packets. A simple prototype packet from Node 1 could contain a structure such as **NODE1, packet_id, soil_moisture, vibration**. A Node 2 packet could contain **NODE2, packet_id, water_level, temperature, pressure**, while Node 3 can add its rainfall value and forward or expose the aggregated information. The final implementation may use JSON or another structured format if appropriate, but the communication protocol should remain lightweight enough for LoRa. Include node identification, packet sequence numbers, timestamps where possible, sensor values, and status/error information.

The system must implement a **disaster-risk/data-fusion engine** rather than merely displaying raw sensor values. The risk engine should combine multiple sensor readings and produce understandable risk states such as **SAFE, LOW, MEDIUM, WARNING, HIGH, and CRITICAL**. For example, a prototype overall risk score can be calculated using weighted values from seismic/vibration activity, soil moisture, water level, rainfall, and environmental conditions. The exact thresholds must be clearly labeled as prototype/demo thresholds and should not be presented as official emergency standards.

For landslide risk, create a dedicated calculation using Node 1's soil moisture and vibration measurements, with rainfall from Node 3 optionally increasing the risk. For example, normal soil moisture plus normal vibration could produce LOW risk, high soil moisture plus normal vibration could produce WARNING, and high soil moisture plus elevated vibration could produce HIGH or CRITICAL risk. The system should allow the threshold values to be calibrated according to the specific sensors and deployment environment. Explain how the thresholds can be modified without rewriting the entire system.

For flood risk, use Node 2's water level and water-level trend together with Node 3's rainfall information. A single water-level reading should not be the only factor. The system should calculate the rate of water-level increase using consecutive readings. For example, if the water level changes from 2.1 m to 2.3 m to 2.7 m to 3.2 m to 3.8 m over a series of measurements, the system should recognize that the water is rising rapidly. If rainfall is also high, the flood-risk score should increase further. This trend-based approach should be explained as an early-warning mechanism rather than a guaranteed prediction.

The system should implement **multi-source data aggregation**. Node 1 provides soil moisture and vibration information, Node 2 provides water level, temperature, and pressure, and Node 3 provides rainfall. The aggregator should combine these sources into one unified disaster-information model. For example, high rainfall plus increasing soil moisture plus elevated vibration should produce an elevated landslide-risk alert, while high rainfall plus rapidly rising water level should produce a flood warning. The dashboard should display both the individual sensor values and the combined risk assessment.

The system should also include **sensor and node health monitoring**. If Node 1, Node 2, or Node 3 stops transmitting data for a defined period, the system should mark that node as OFFLINE or show a sensor-failure warning. Every node should maintain a last-seen timestamp or packet sequence number. The dashboard should show whether each node is ONLINE, OFFLINE, or experiencing communication problems. This feature is especially important in rural disaster monitoring because a missing sensor should not silently appear as normal conditions.

The local gateway computer should run a **Python-based backend using FastAPI**.
